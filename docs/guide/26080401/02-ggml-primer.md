# 02. 코드를 읽기 위한 GGML과 GGUF 기초

NanoEmbed의 `src/forward/*.cpp`는 대부분 짧다. 어려운 점은 코드 길이가 아니라 ggml이 텐서와 메모리를 표현하는 방식이다.

이 장에서는 다음 질문에 답한다.

- 텐서는 어떤 정보와 실제 데이터로 구성되는가?
- 연산 함수를 호출했는데 왜 계산이 즉시 일어나지 않는가?
- `ggml_context`와 `ggml_gallocr`는 각각 무엇을 소유하는가?
- 모델 가중치와 중간 활성값은 어떻게 다른가?
- GGUF 파일에는 무엇이 저장되는가?

## 텐서는 설명과 데이터로 나뉜다

텐서를 다차원 숫자 배열이라고 생각하면 출발점으로 충분하다. 하지만 구현에서는 두 부분을 구분해야 한다.

### 텐서 메타데이터

메타데이터는 배열을 해석하는 정보다.

- 자료형: F32, F16, Q8_0 등
- 차원 수
- 각 축의 길이, 즉 차원 크기(shape) `ne`
- 각 축으로 한 칸 이동할 때의 바이트 수 `nb`
- 실제 데이터 주소
- 이 텐서를 만든 연산과 입력 텐서

`ggml_tensor` 구조체가 이 정보를 가진다. 숫자 배열 전체에 비하면 작지만, 그래프 안의 모든 중간 텐서마다 하나씩 필요하다.

### 텐서 데이터

데이터는 실제 숫자가 저장되는 바이트 영역이다. 같은 차원 크기의 텐서라도 F32이면 원소당 4바이트, F16이면 2바이트를 사용한다. 양자화 자료형은 여러 값을 묶어 더 적은 바이트에 저장한다.

다음 두 텐서는 같은 `ggml_tensor` 구조를 사용하지만 수명이 다르다.

- 모델 가중치 `attn_q.weight`: GGUF에서 읽으며 모델이 살아 있는 동안 유지된다.
- Q 선형 변환 결과: 한 번의 순전파 중에만 필요하며 계산이 끝나면 재사용할 수 있다.

이 차이가 NanoEmbed의 메모리 설계에서 중요하다.

## 실행 중 메모리의 종류

NanoEmbed를 실행하면 크게 네 종류의 메모리가 생긴다.

| 종류 | 예 | 만들어지는 시점 | 유지되는 기간 | 현재 소유자 |
|---|---|---|---|---|
| 모델 가중치 | Q·K·V 행렬, 임베딩 표 | 모델 로드 | 모델 해제까지 | `nanoembed_model` |
| 토크나이저·모델 정보 | 어휘, 레이어 수 | 모델 로드 | 모델 해제까지 | `nanoembed_model` |
| 그래프 메타데이터 | 텐서 차원 크기와 연산 관계 | 각 순전파 그래프 구성 | 해당 그래프 종료까지 | `ComputeScratch`의 메타데이터 영역 |
| 입력·활성값 데이터 | 토큰 ID, Q·K·V, FFN 출력 | 그래프 할당과 실행 | 다음 실행에서 재사용 가능 | `ComputeScratch`의 그래프 버퍼 |

문서에서 “그래프 버퍼”라고 부르는 것은 마지막 행이다. 계산 중간 결과를 저장하는 데이터 메모리다. 계산 그래프를 설명하는 작은 구조체만 가리키는 표현이 아니다.

## `ggml_context`의 역할

`ggml_context`는 텐서와 계산 그래프를 만들 때 사용하는 메모리 문맥이다. 생성할 때 `ggml_init_params`로 메모리와 할당 방식을 지정한다.

중요한 설정은 `no_alloc`이다.

### `no_alloc = false`

텐서 메타데이터와 실제 데이터를 컨텍스트의 메모리 영역에 함께 할당한다. 구현이 단순하다. 텐서를 만들면 곧바로 데이터 주소가 생긴다.

초기 M3 구현이 이 방식을 사용했다. `embed()`마다 256 MiB 연속 영역을 만들고 모든 중간 텐서의 데이터를 앞에서부터 배치했다.

이 방식에서는 그래프 앞부분의 중간 텐서를 더 이상 사용하지 않더라도 그 공간을 뒤의 텐서가 재사용하지 않는다. 컨텍스트 전체를 해제할 때까지 앞에서 할당한 공간이 남는다.

256 MiB는 BERT 계산에 반드시 필요한 크기가 아니었다. 필요한 크기를 정확히 분석하지 않고 선택한 보수적인 고정 용량이었다. 길이 512 입력에는 이 용량도 부족할 수 있었다.

### `no_alloc = true`

텐서 메타데이터만 만든다. 텐서의 `data`는 아직 없다. 계산 그래프 전체를 만든 뒤 별도 할당기가 실제 데이터 공간을 배치할 수 있다.

현재 NanoEmbed가 이 방식을 사용한다.

```cpp
ggml_init_params p;
p.mem_size   = meta_buf.size();
p.mem_buffer = meta_buf.data();
p.no_alloc   = true;
ggml_context * gctx = ggml_init(p);
```

`meta_buf`에는 `ggml_tensor` 구조체와 그래프 설명만 들어간다. 입력과 중간 활성값의 실제 데이터는 `ggml_gallocr`가 관리한다.

## 그래프를 만드는 단계와 실행하는 단계

ggml의 연산 함수는 기본적으로 지연 실행된다. 예를 들어 다음 호출은 행렬곱을 즉시 계산하지 않는다.

```cpp
ggml_tensor * q = ggml_mul_mat(ctx, w.q_w, x);
```

이 호출은 다음 정보를 가진 출력 텐서를 만든다.

- 연산 종류는 행렬곱이다.
- 입력은 `w.q_w`와 `x`다.
- 결과의 차원 크기와 자료형은 무엇이다.

실제 숫자 계산은 나중에 백엔드가 그래프를 실행할 때 일어난다.

NanoEmbed의 한 번의 순전파는 다음 단계로 나뉜다.

### 1단계: 입력과 연산 노드를 만든다

토큰 ID 입력 텐서를 만들고, 임베딩부터 최종 출력까지 연산을 연결한다.

```cpp
ggml_tensor * x = arch->build_graph(gctx, inputs);
ggml_tensor * out = forward::build_pool(gctx, x, pooling);
```

이 시점에는 아직 입력 데이터나 중간 활성값을 저장할 공간이 없다.

### 2단계: 최종 출력에서 역으로 그래프를 수집한다

```cpp
ggml_cgraph * graph = ggml_new_graph(gctx);
ggml_build_forward_expand(graph, out);
```

ggml은 `out`을 만들기 위해 필요한 입력과 연산을 따라가서 실행 순서를 만든다.

### 3단계: 그래프 데이터 공간을 배치한다

```cpp
ggml_gallocr_alloc_graph(galloc, graph);
```

이 호출 뒤에 입력 텐서와 중간 텐서가 실제 데이터 주소를 가진다.

### 4단계: 입력 값을 복사한다

```cpp
ggml_backend_tensor_set(token_ids, ids.data(), 0, id_bytes);
```

입력 텐서는 할당 전에는 데이터 주소가 없으므로 반드시 3단계 뒤에 값을 넣어야 한다.

### 5단계: CPU에서 그래프를 실행한다

```cpp
ggml_backend_graph_compute(backend, graph);
```

이때 행렬곱, softmax, 정규화 같은 실제 계산이 일어난다.

### 6단계: 최종 결과를 읽는다

```cpp
ggml_backend_tensor_get(out, output, 0, output_bytes);
```

그래프 안의 출력 텐서에서 호출자가 제공한 `float` 배열로 값을 복사한다.

## `ggml_gallocr`와 버퍼 재사용

`ggml_gallocr`는 그래프 전용 할당기다. 그래프의 실행 순서를 알기 때문에 각 중간 텐서가 언제 마지막으로 사용되는지 계산할 수 있다.

간단한 그래프를 생각해 보자.

```text
A와 B로 C 계산
C와 D로 E 계산
E로 F 계산
```

E를 만든 뒤에는 C가 다시 필요하지 않다. F를 위한 메모리는 C가 사용했던 공간을 재사용할 수 있다.

```text
시간 ──────────────────────────────────────▶

C 버퍼: [ C가 살아 있는 구간 ]
                         [ F가 같은 공간 재사용 ]
E 버퍼:          [ E가 살아 있는 구간 ]
```

초기 M3의 단순한 컨텍스트 할당은 이런 재사용을 하지 않았다. 현재 구현은 `ggml_gallocr`가 수명을 분석해 하나의 그래프 버퍼 안에서 공간을 겹쳐 쓴다.

`ggml_gallocr_reserve()`는 최대 입력 길이의 그래프를 한 번 만들어 필요한 버퍼 크기를 미리 계산한다. 이후 더 짧은 입력은 같은 버퍼를 사용한다. 버퍼가 컨텍스트에 속하므로 모델 하나에 컨텍스트가 여러 개 있으면 각 컨텍스트가 자기 버퍼를 가진다.

## 입력과 출력을 표시하는 이유

입력 텐서는 그래프를 할당한 뒤 외부 데이터로 채운다. 출력 텐서는 계산이 끝난 뒤 외부로 읽는다.

```cpp
ggml_set_input(token_ids);
ggml_set_output(out);
```

이 표시는 할당기에게 두 텐서의 데이터가 언제까지 유지되어야 하는지 알려 준다.

- 입력 공간은 값을 넣은 뒤 그 값을 사용하는 모든 연산이 끝날 때까지 보존해야 한다.
- 출력 공간은 그래프 마지막까지 살아 있어야 한다.

표시가 없으면 할당기가 아직 외부에서 읽거나 쓸 공간을 다른 중간 텐서와 겹치게 배치할 수 있다.

## CPU 백엔드

백엔드는 그래프를 실제로 어느 장치에서 실행할지 나타낸다. ggml은 CPU, Metal, CUDA 같은 백엔드를 제공할 수 있다.

현재 NanoEmbed는 컨텍스트마다 CPU 백엔드를 만든다.

```cpp
ggml_backend_t backend = ggml_backend_cpu_init();
ggml_backend_cpu_set_n_threads(backend, n_threads);
```

모델 가중치는 현재 일반 `ggml_context`가 소유하는 호스트 메모리에 있다. CPU 백엔드는 이 포인터를 직접 읽는다. M4에서 `mmap`과 다른 백엔드 버퍼를 도입할 때는 가중치가 어느 버퍼에 속하는지 다시 검토해야 한다.

## ggml의 축 순서

일반적인 머신러닝 문서는 텐서 차원 크기를 `[B, S, H]`처럼 쓴다.

- `B`: batch, 동시에 처리하는 문장 수
- `S`: sequence, 문장 안의 토큰 수
- `H`: hidden, 토큰 하나를 표현하는 벡터 길이

ggml의 `ne[0]`은 메모리에서 가장 연속적인 축이다. NanoEmbed는 같은 활성값을 `[H, S, B]`로 표현한다.

```text
ne[0] = H  토큰 벡터 안의 원소
ne[1] = S  문장 안의 토큰 위치
ne[2] = B  배치의 문장 위치
```

bge-small에서 문장 하나가 20토큰이면 차원 크기는 다음과 같다.

```text
[H, S, B] = [384, 20, 1]
```

`ne[0]`이 연속적이므로 한 토큰의 384개 값이 메모리에 이어서 놓인다.

### `nb`는 바이트 단위 stride다

`nb[i]`는 해당 축에서 한 칸 이동할 때 건너뛸 바이트 수다.

F32 `[384, 20, 1]` 텐서가 연속적으로 저장되었다고 가정하면 다음과 비슷하다.

```text
nb[0] = 4                 다음 hidden 값까지 4바이트
nb[1] = 384 × 4           다음 토큰까지 1,536바이트
nb[2] = 20 × 384 × 4      다음 문장까지 30,720바이트
```

`ggml_permute`는 데이터를 바로 복사하지 않고 `ne`와 `nb`의 해석만 바꾼 텐서를 만든다. 원본 데이터를 다른 축 순서로 바라보는 보기(view)다. 이렇게 만든 텐서는 메모리가 연속적이지 않을 수 있다. 뒤의 연산이 연속 메모리를 요구하면 `ggml_cont`로 새 연속 텐서를 만든다.

## `ggml_mul_mat` 읽는 법

NanoEmbed의 가중치 주석은 ggml 축 순서로 작성되어 있다.

```text
up_w: [H, F]
x:    [H, S, B]
결과: [F, S, B]
```

```cpp
ggml_tensor * h = ggml_mul_mat(ctx, up_w, x);
```

두 입력의 `ne[0]`, 여기서는 H축을 곱해서 더한다. 문서의 보통 행렬 표기와 인자 방향이 낯설 수 있으므로, 호출만 보지 말고 입력과 출력의 차원 크기를 함께 확인하는 편이 안전하다.

어텐션에서는 같은 규칙으로 `KᵀQ` 점수와 `V`의 가중합을 계산한다. 구체적인 차원 변화는 03장과 05장에서 단계별로 설명한다.

## GGUF 파일에는 무엇이 들어 있는가

GGUF는 다음 세 영역을 한 파일에 저장한다.

### 메타데이터

키와 값의 모음이다.

```text
general.architecture = "bert"
bert.block_count = 12
bert.embedding_length = 384
tokenizer.ggml.model = "bert"
```

NanoEmbed는 이 값을 읽어 모델 구조, 차원과 토크나이저 종류를 결정한다.

### 텐서 설명

각 가중치의 이름, 자료형, 차원 크기와 파일 안의 위치를 기록한다.

```text
token_embd.weight
blk.0.attn_q.weight
blk.0.ffn_up.weight
```

모델 구조마다 필요한 이름과 차원 크기가 다르다. BERT 검사기는 모델을 실행하기 전에 모든 필수 텐서를 확인한다.

### 텐서 데이터

F16이나 양자화 형식으로 저장된 실제 가중치 바이트다. 메타데이터만 검사할 때는 이 데이터를 할당하지 않아도 된다. 실제 추론용으로 열 때는 가중치 텐서가 데이터 주소를 가져야 한다.

## GGUF를 두 가지 목적으로 여는 이유

현재 BERT 로드 경로는 같은 파일을 두 번 연다.

1. `no_alloc=true`로 열어 메타데이터와 텐서 구성이 올바른지 검사한다.
2. `no_alloc=false`로 다시 열어 실제 가중치 데이터를 가진 모델 컨텍스트를 만든다.

첫 번째 경로의 목적은 잘못된 모델을 구체적인 오류와 함께 일찍 거부하는 것이다. 두 번째 경로는 실제 계산에 사용할 포인터를 제공한다.

M4에서는 모든 가중치를 일반 메모리에 복사하는 현재 방식이 바뀔 예정이다. 검사와 실제 실행용 소유권을 구분하는 이유는 그대로 유지된다.

## 현재 `Embedder::embed()`를 ggml 관점에서 보기

```text
1. 텍스트를 토큰 ID로 변환한다.
2. 컨텍스트의 CPU 백엔드와 그래프 할당기를 선택한다.
3. 메타데이터 전용 ggml_context를 만든다.
4. 입력, BERT 인코더, 풀링, 정규화 노드를 만든다.
5. ggml_gallocr가 데이터 버퍼를 배치한다.
6. 토큰·위치·타입 ID를 입력 텐서에 복사한다.
7. CPU 백엔드가 그래프를 실행한다.
8. 최종 임베딩을 호출자 배열로 복사한다.
9. 그래프 메타데이터 컨텍스트만 해제한다.
10. 활성값 버퍼는 ComputeScratch에 남아 다음 호출에서 재사용된다.
```

모델 가중치는 1회 로드 후 계속 유지된다. 그래프 메타데이터는 호출마다 새 그래프를 설명하기 위해 다시 만들고, 큰 활성값 데이터 버퍼는 컨텍스트와 함께 유지한다.

## 이 장의 핵심 정리

- `ggml_tensor`의 설명과 실제 데이터는 별도 메모리에 둘 수 있다.
- ggml 연산 호출은 계산을 즉시 실행하지 않고 그래프 노드를 만든다.
- 현재 NanoEmbed는 `no_alloc=true` 컨텍스트로 그래프를 설명하고 `ggml_gallocr`로 데이터 버퍼를 배치한다.
- `ggml_gallocr`는 사용이 끝난 중간 텐서 공간을 뒤의 텐서가 재사용하게 한다.
- 모델 가중치는 모델 수명 동안 유지되고, 활성값 버퍼는 컨텍스트가 소유한다.
- NanoEmbed 활성값의 기본 축 순서는 `[H, S, B]`다.
- GGUF에는 메타데이터, 텐서 설명과 실제 가중치가 함께 들어 있다.
