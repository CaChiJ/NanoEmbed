# 08. 코드 규칙과 확장 지점

이 장은 기능을 추가할 때 현재 구조를 어떻게 유지할지 설명한다. 스타일 규칙만 나열하지 않고 각 경계가 어떤 문제를 막는지 함께 설명한다.

## 의존성 방향

현재 주요 의존성은 다음 방향으로 흐른다.

```text
공개 C API
  → C API 구현
    → Embedder
      ├─ ModelArch
      ├─ Tokenizer
      └─ 공통 pool
          → BERT forward 빌더
            → ggml
```

상위 계층은 아래 계층을 조정한다. 아래 계층은 상위 계층의 정책을 알지 않는다.

예를 들어 `attention.cpp`는 다음 정보만 받는다.

- 그래프를 만들 `ggml_context`
- 입력 텐서
- 선택적 어텐션 마스크
- 헤드 수
- 이 레이어의 가중치
- LayerNorm epsilon

이 함수는 공개 C 설정, 모델 파일 경로, 컨텍스트 핸들이 무엇인지 알 필요가 없다.

반대로 `c_api.cpp`에서 Q·K·V 텐서를 직접 만들기 시작하면 공개 경계와 모델 계산 책임이 섞인다. 새 기능을 넣기 전에 어느 계층의 결정인지 먼저 확인한다.

## 디렉터리별 책임

| 책임 | 위치 |
|---|---|
| 외부에 약속한 C 함수와 타입 | `include/nanoembed/` |
| 포인터 검사와 예외 변환 | `src/api/` |
| 모델·컨텍스트 실행 흐름 조정 | `src/embedder.*` |
| GGUF 모델 구조 선택과 모델별 그래프 | `src/arch/` |
| 문자열을 토큰 ID로 변환 | `src/tokenizer/` |
| 모델 계산의 작은 ggml 그래프 함수 | `src/forward/` |
| 사용자·개발 도구 | `tools/` |
| 기능과 성능 검증 | `tests/`, `bench/` |

새 파일은 이름이 비슷한 곳이 아니라 책임이 맞는 곳에 둔다.

## 공개 헤더와 내부 헤더

`include/nanoembed/nanoembed.h`는 설치 대상이 될 공개 C 헤더다.

- C11로 컴파일할 수 있어야 한다.
- C++ 표준 라이브러리와 ggml 타입을 노출하지 않는다.
- 구조체 내부 구현을 공개하지 않는다.
- 새 enum 값은 기존 숫자를 바꾸지 않고 끝에 추가한다.

`src/` 헤더는 내부 구현이다. 공개 API를 사용하는 도구는 가능하면 내부 헤더를 포함하지 않는다.

내부를 직접 검사해야 하는 `nanoembed-inspect`와 일부 단위 테스트만 CMake에서 `src/` include 경로를 명시적으로 받는다.

## 이름 규칙

주변 코드와 같은 규칙을 사용한다.

| 대상 | 형식 | 예 |
|---|---|---|
| 타입과 클래스 | `PascalCase` | `ModelArch`, `ComputeScratch` |
| 함수와 지역 변수 | `snake_case` | `create_tokenizer`, `max_seq_len` |
| 클래스 필드 | 뒤에 `_` | `params_`, `manifest_` |
| C API | `nanoembed_` 접두사 | `nanoembed_embed` |
| 공개 enum 값 | `NANOEMBED_` 접두사 | `NANOEMBED_POOL_CLS` |
| ggml 텐서 축 기호 | 대문자 한 글자 | `H`, `S`, `B`, `F` |

축 기호를 사용하면 가까운 주석이나 문서에서 뜻을 적는다.

```text
H = hidden 차원
S = 토큰 수
B = batch 크기
F = FFN 중간 차원
```

## include와 빌드 경계

`.cpp` 파일의 include는 보통 다음 순서를 따른다.

1. 대응하는 자기 헤더
2. 프로젝트 내부 헤더
3. ggml·GGUF 같은 외부 헤더
4. 플랫폼 헤더
5. C++ 표준 라이브러리

공개 또는 넓게 포함되는 헤더에서는 가능한 경우 ggml 구조체를 전방 선언한다. `ggml.h`를 헤더에 직접 포함하면 그 헤더를 사용하는 모든 파일의 컴파일 비용과 결합도가 늘어난다.

새 실행 파일이나 테스트를 추가할 때는 다음을 확인한다.

- 공개 API만 쓰면 `nanoembed_core`에만 링크한다.
- 내부 타입을 검사해야 할 때만 `src/` include와 `ggml::ggml` 링크를 추가한다.
- `NANOEMBED_WARNING_FLAGS`를 NanoEmbed 대상에 적용한다.
- Linux `/proc`에 의존하는 코드는 플랫폼 조건 안에 둔다.

## 메모리 소유권을 먼저 적는다

ggml 포인터를 필드나 함수 인자로 추가할 때는 누가 해제하는지 분명해야 한다.

현재 주요 소유권은 다음과 같다.

| 자원 | 소유자 | 수명 |
|---|---|---|
| 실행용 `gguf_context` | `Embedder::Impl` | 모델 수명 |
| 가중치 `ggml_context` | `Embedder::Impl` | 모델 수명 |
| `ModelArch`, `Tokenizer` | `Embedder::Impl` | 모델 수명 |
| CPU 백엔드 | `ComputeScratch::Impl` | 컨텍스트 수명 |
| `ggml_gallocr`와 그래프 버퍼 | `ComputeScratch::Impl` | 컨텍스트 수명 |
| 그래프 메타데이터 `ggml_context` | 한 번의 `reserve` 또는 `embed` 호출 | 호출 종료까지 |
| 공개 출력 배열 | 호출자 | 호출자가 정한 수명 |

빌린 포인터를 소유 포인터처럼 해제하거나, 소유 객체보다 오래 보관하면 use-after-free 또는 이중 해제가 생긴다.

소멸자는 참조 관계의 반대 순서로 해제한다. 예를 들어 텐서가 가리키는 `ggml_context`를 먼저 없앤 뒤 그 데이터를 추적하는 GGUF 핸들을 해제한다.

## 오류는 발견 가능한 가장 이른 경계에서 보고한다

문제를 알 수 있는 시점과 보고하는 시점을 가깝게 둔다.

- 파일 구조와 텐서 차원 크기 문제는 모델 로드에서 보고한다.
- 컨텍스트 설정의 음수나 미지원 스트리밍은 컨텍스트 생성에서 보고한다.
- `nullptr` 입력은 공개 함수 진입에서 보고한다.
- 그래프 할당과 실행 실패는 해당 ggml 호출 직후 보고한다.

지원하지 않는 기능을 비슷한 기본 동작으로 조용히 바꾸지 않는다. `use_streaming=1`을 인메모리 실행으로 무시하면 사용자는 메모리 제한을 지켰다고 잘못 판단할 수 있다.

내부 예외 메시지에는 가능한 경우 다음 정보를 넣는다.

- 실패한 파일이나 텐서 이름
- 예상값과 실제값
- GGUF가 선언한 모델 또는 토크나이저 종류
- 사용자가 바꿀 수 있는 설정값

## 주석은 코드에서 보이지 않는 이유를 설명한다

코드 자체를 한국어 또는 영어 문장으로 다시 읽어 주는 주석은 오래 유지되지 않는다.

다음 정보는 주석에 가치가 있다.

- `ggml_set_input()`을 빼면 할당기가 왜 잘못 재사용할 수 있는지
- Apple에서 전체 논리 코어 대신 성능 코어를 선택하는 이유
- `ggml_permute` 뒤에 `ggml_cont`가 필요한 이유
- GELU 근사 버전이 아니라 erf 버전을 쓰는 정확도 이유
- 아직 구현하지 않은 기능과 해당 마일스톤

마일스톤을 언급할 때는 `M4에서 구현 예정`처럼 자연스러운 문장으로 쓴다. `lands in M4` 같은 내부적인 영어 표현은 피한다.

## 새 풀링 방식 추가

풀링은 모델 구조와 공개 API 양쪽에 영향을 줄 수 있다.

1. `src/forward/pool.*`에 `[H,S,B] → [H,B]` 그래프 함수를 추가한다.
2. 내부 `forward::PoolType`과 `nanoembed::PoolType`을 갱신한다.
3. `Embedder`의 내부 enum 변환을 갱신한다.
4. 사용자가 선택해야 한다면 공개 C enum 끝에 값을 추가한다.
5. `from_params()`가 공개 enum을 내부 enum으로 올바르게 바꾸는지 확인한다.
6. 작은 텐서 단위 테스트와 공개 API 기준값 테스트를 추가한다.
7. 패딩이 있는 실제 배치에서 유효 토큰을 어떻게 찾을지 정의한다.

내부에는 Last 풀링이 이미 있다. 하지만 공개 C API에는 Mean과 CLS만 있다. eurobert 지원에서 Last를 사용자에게 노출한다면 기존 enum 숫자를 바꾸지 않고 끝에 추가해야 한다.

## 새 모델 구조 추가

새 GGUF 모델 구조는 `ModelArch` 구현으로 추가한다.

1. GGUF의 `general.architecture` 실제 값을 확인한다.
2. 모델 전용 메타데이터와 필수 텐서 차원 크기를 검증한다.
3. 공통 `ArchParams`를 채운다.
4. 필요한 입력이 token, position, type ID 중 무엇인지 선언한다.
5. 학습된 기본 풀링 방식을 반환한다.
6. 실행용 `model_ctx`에서 가중치 포인터를 연결한다.
7. `[H,S,B]` 인코더 출력을 만드는 `build_graph()`을 구현한다.
8. `src/arch/registry.cpp`에 `general.architecture` 분기를 추가한다.

모델마다 다른 계산을 기존 BERT 함수에 조건문으로 계속 넣지 않는다. BERT의 learned position embedding과 eurobert의 RoPE처럼 계산 자체가 다르면 별도 구현이 책임져야 한다.

공유할 수 있는 작은 연산이 확인되면 `src/forward/` 함수로 분리한다. 두 번째 구현이 생기기 전에 이름만 일반적인 추상화를 먼저 만들지는 않는다.

## 새 토크나이저 추가

토크나이저는 모델 구조와 별도로 추가한다.

1. `Tokenizer`를 구현한다.
2. GGUF 메타데이터에서 어휘와 특수 토큰을 읽는다.
3. `encode()`가 특수 토큰을 포함해 길이 상한을 지키게 한다.
4. `src/tokenizer/registry.cpp`에 `tokenizer.ggml.model` 분기를 추가한다.
5. Hugging Face가 만든 토큰 ID 기준 데이터를 추가한다.
6. 빈 문자열, 구두점, 알 수 없는 글자, 길이 경계와 Unicode 입력을 검사한다.

GPT-2 계열 byte-level BPE는 WordPiece와 어휘 표기, pre-tokenization과 병합 알고리즘이 다르다. WordPiece 클래스 안에 모드를 추가하기보다 별도 구현으로 추가한다.

## 새 실행 백엔드 추가

현재 `ComputeScratch`는 CPU 백엔드를 직접 만든다. Metal이나 CUDA를 추가하려면 단순히 생성 함수 하나만 바꾸는 것으로 끝나지 않을 수 있다.

확인해야 할 항목은 다음과 같다.

- 모델 가중치가 해당 백엔드의 버퍼에 있어야 하는가?
- 입력 데이터 복사는 어떤 API와 동기화가 필요한가?
- `ggml_gallocr`가 사용하는 buffer type은 무엇인가?
- 컨텍스트마다 백엔드를 만들지, 공유할지?
- 공개 설정에 장치 선택을 추가할지?
- CPU 기준값과 어느 정도의 수치 차이를 허용할지?

현재 가중치는 일반 호스트 메모리에 있고 CPU 백엔드가 직접 읽는다. 이 전제를 GPU 백엔드에 그대로 적용하면 안 된다.

## M4 스트리밍을 구현할 때 유지할 경계

M4의 목적은 모델 가중치 수명을 줄이는 것이다. 활성값 버퍼 재사용과는 다른 문제다.

스트리밍 실행은 다음 흐름을 책임져야 한다.

```text
공통 임베딩 계산
  → 레이어 i 가중치 준비
  → 레이어 i 그래프 구성과 실행
  → 출력 활성값 보존
  → 레이어 i 가중치 페이지 반환
  → 다음 레이어
```

구현 전에 다음을 결정하고 테스트로 고정한다.

- 토큰 임베딩과 정규화 가중치 중 계속 상주할 항목
- 한 레이어의 가중치를 복사 없이 직접 가리킬지 백엔드 버퍼로 복사할지
- 레이어가 바뀌어도 유지해야 하는 활성값의 소유자
- 예외가 발생했을 때 현재 레이어 자원을 정리하는 방법
- `madvise(DONTNEED)` 뒤 실제 RSS가 언제 내려가는지
- 현재 인메모리 경로와 결과가 같은지

M3.5 기준 측정값을 유지한 채 가중치 영역만 바뀌는 시나리오를 비교해야 한다.

## M5 실제 배치를 구현할 때

현재 `nanoembed_embed_batch()`는 단일 경로 반복이다. 실제 배치는 텐서의 B축을 1보다 크게 만들고 패딩을 도입한다.

필요한 변경은 다음과 같다.

- 길이가 비슷한 문장을 묶는 버킷팅
- `[H,S,B]` 활성값
- 패딩 위치를 막는 어텐션 마스크
- Mean 풀링에서 패딩 제외
- Last 풀링에서 문장별 마지막 유효 위치 선택
- `max_batch` 초과 입력의 내부 분할
- 출력이 원래 입력 순서로 돌아오는지 확인

배치는 정확도뿐 아니라 메모리도 바꾼다. `B × S × H` 활성값이 늘어나므로 처리량만 보고 배치 크기를 정하지 않는다.
