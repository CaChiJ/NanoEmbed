# 패딩 제거: M5 성능 문제를 해결한 두 단계

작성일: 2026-08-30

M5 측정에서 배치의 성능 저하 원인이 패딩으로 확인된 뒤, 실제로 패딩 계산을
없앤 작업의 기록이다. 두 단계로 진행했고 결과는 다음과 같다.

| 구현 | 배치 1 → 10 (warm, 길이 혼합) |
|---|---:|
| ① 원래 방식 (마스크) | −28% |
| ② 어텐션만 문장별로 분리 | −14% |
| ③ 모든 토큰 단위 연산에서 패딩 제거 | **+44%** |

cold 조건(디스크에서 처음 읽음)에서도 +523%에서 **+607%**로 좋아졌다.

배치가 클수록 이득이 커진다. 배치 10에서 ③은 ①보다 **처리량이 96% 높다.**

---

## 1. 문제였던 것

배치는 문장 여러 개를 하나의 직사각형 배열에 담는다. 길이가 다르면 가장 긴
문장에 맞춰 빈칸(패딩)을 채운다.

길이 4·7·12인 문장 3개라면:

```
      ←──────── 12칸 ────────→
문장1 │●●●●░░░░░░░░│
문장2 │●●●●●●●░░░░░│
문장3 │●●●●●●●●●●●●│

진짜 토큰 23칸, 계산하는 칸 36칸 → 13칸(36%)이 낭비
```

이 빈칸도 CPU가 똑같이 계산한 뒤 버린다. 그리고 어텐션에서는 빈칸이 결과를
오염시키지 않도록 마스크라는 표를 따로 만들어 씌운다.

**중요한 사실 하나**: ggml은 마스크된 칸을 건너뛰지 않는다. 점수판은 마스크를
적용하기 전에 이미 만들어지고([ggml-cpu.c](../third_party/ggml/src/ggml-cpu/ggml-cpu.c)의
`ggml_mul_mat`), softmax도 패딩 폭까지 전부 훑는다
([ops.cpp:5299 이후](../third_party/ggml/src/ggml-cpu/ops.cpp#L5299)).
즉 마스크는 결과를 맞추는 장치일 뿐 계산을 줄이지 않는다. **미리 잘라내야 실제로
계산을 안 한다.**

---

## 2. 1단계: 어텐션을 문장별로 분리

### 무엇을 바꿨나

어텐션은 각 토큰이 문장 안의 모든 칸을 훑는 연산이다. 문장마다 자기 길이로
따로 계산하도록 바꿨다.

```
전:  12×12 점수판 3장 = 432칸 → 마스크로 223칸 무효화
후:  4×4 + 7×7 + 12×12 = 209칸 → 마스크 불필요
```

어텐션은 길이의 **제곱**으로 비용이 커지므로 빈칸의 손해가 여기서 가장 크다.

구현은 [src/forward/gqa_attention.cpp](../src/forward/gqa_attention.cpp)에 있다.
문장별 구간을 view로 잘라내므로 복사가 없고, 결과는 다시 원래 모양으로 되돌린다.

### 결과

**정확도가 완전히 해결됐다.**

| 모델 | 변경 전 최대 오차 | 변경 후 |
|---|---:|---:|
| harrier F32 | 4.361e-5 | **0** |
| harrier Q8 | 2.98e-8 | **0** |

harrier는 문장을 하나씩 처리한 결과와 완전히 같아졌다. M5가 넘지 못했던 원래
기준(1e-5)을 통과한다.

원인은 덧셈 순서였다. 마스크가 있으면 softmax가 패딩 칸까지 훑는데, 그 칸들은
결과에 기여하지 않으면서 연산에는 포함되어 반올림이 달라진다. 실제 길이만
계산하면 순차 처리와 연산이 같아진다.

**성능은 절반만 해결됐다.** −28%가 −14%로 줄었지만 방향은 그대로였다.

이유는 두 가지였다. 문장별 결과를 다시 하나로 되돌리는 조립 비용이 새로 생겼고,
더 중요하게는 **전체 계산의 약 95%를 차지하는 나머지 연산이 여전히 빈칸을
계산하고 있었다.**

---

## 3. 2단계: 토큰 단위 연산에서 패딩 제거

### 왜 가능한가

연산을 두 부류로 나누면 답이 나온다.

| 연산 | 문장 경계를 알아야 하나 |
|---|---|
| 임베딩 조회, 정규화, Q·K·V·O 선형 변환, FFN | **모름** — 토큰 하나 받아 토큰 하나 내놓음 |
| 어텐션 | 알아야 함 |
| 풀링 | 알아야 함 |

FFN은 자기가 처리하는 토큰이 몇 번 문장 소속인지 상관하지 않는다. 그러니
빈칸을 빼고 진짜 토큰만 이어서 계산해도 **결과가 완전히 같다.**

그리고 문장 간 간섭이 가능한 유일한 연산인 어텐션은 1단계에서 이미 분리했다.
그래서 안전하다 — 순서가 중요했다.

### 무엇을 바꿨나

빈칸을 채운 배열 대신, 진짜 토큰만 이어 붙인 배열을 함께 만든다.

```
전:  ●●●●░░░░░░░░ ●●●●●●●░░░░░ ●●●●●●●●●●●●   36칸
후:  ●●●● ●●●●●●● ●●●●●●●●●●●●                23칸
     └문장1┘└─문장2─┘└──문장3──┘
     어디서 시작하는지는 offsets가 기록
```

| 파일 | 역할 |
|---|---|
| [src/batch.cpp](../src/batch.cpp) | 패딩 없는 배열과 문장별 시작 위치 생성 |
| [src/forward/gqa_attention.cpp](../src/forward/gqa_attention.cpp) | 고정 간격 대신 시작 위치로 문장을 잘라냄 |
| [src/forward/pool.cpp](../src/forward/pool.cpp) | 문장마다 자기 구간만 집계 — 마스크·보정값 불필요 |
| [src/embedder.cpp](../src/embedder.cpp), [src/streaming_execution.cpp](../src/streaming_execution.cpp) | 패킹된 입력 공급 |

**길이가 이미 같은 묶음은 기존 경로를 그대로 쓴다.** 그 경우 빈칸이 없어 바꿀
이유가 없고, 실제로 측정해도 달라지지 않는다.

아키텍처가 지원을 선언해야 켜진다(`InputRequirements::consumes_packed_batch`).
현재 gemma3(harrier)만 사용하고 BERT는 기존 마스크 경로를 유지한다.

### 구현 중 잡은 결함

패킹 여부를 임베딩 단계는 아키텍처 기준으로, 레이어 그룹은 그룹에 속한 유닛
기준으로 판단하고 있었다. 어텐션이 없는 FFN 전용 그룹은 지원을 선언하지 않으므로
활성값은 23칸인데 위치 배열은 12칸으로 만들어져 `ggml_rope_ext`가 중단됐다.

패킹은 **묶음 전체의 성질**이지 그룹의 성질이 아니다. 판단을 한 곳에서 내리고
임베딩·모든 그룹·최종 풀링이 같은 값을 쓰도록 고쳤다.

## 4. 측정 결과

Harrier Q8, mixed_short 132문장, warm, streaming, layer 파티션, 스레드 4개.
3회 독립 실행의 중앙값이다.

배치 1은 코드 경로가 바뀌지 않으므로 **측정 오염을 판별하는 대조군**으로 썼다.
기준선 41.4에서 크게 벗어난 실행은 버렸다(실제로 두 번 버렸다).

### 처리량 (문장/초, 높을수록 좋음)

| 배치 | ① 마스크 | ② 문장별 어텐션 | ③ 패킹 | ③ vs ① |
|---:|---:|---:|---:|---:|
| 1 | 41.4 | 41.3 | 40.8 | −2% (대조군) |
| 2 | 40.6 | 43.5 | 49.5 | +22% |
| 3 | 39.7 | 42.8 | 53.0 | +34% |
| 4 | 38.3 | 42.6 | 56.0 | +46% |
| 5 | 36.5 | 40.3 | 57.2 | +57% |
| 10 | 30.0 | 35.4 | **58.8** | **+96%** |

### 각 구현 안에서 배치를 키웠을 때

```
① 마스크        41.4 → 30.0   −28%
② 문장별 어텐션  41.3 → 35.4   −14%
③ 패킹          40.8 → 58.8   +44%
```

실행 간 편차는 중앙값 3.4%다. +44%는 그보다 훨씬 크다.

### 메모리 (PSS 평균, MiB)

| 배치 | 마스크 | 패킹 | 변화 |
|---:|---:|---:|---:|
| 1 | 18.3 | 18.2 | −0% |
| 2 | 22.9 | 22.5 | −2% |
| 5 | 33.0 | 25.9 | **−21%** |
| 10 | 34.4 | 31.0 | −10% |

활성값이 작아진 만큼 줄었다. USS도 같은 경향이다(−22%, −10%).

### cold 캐시 (디스크에서 처음 읽는 조건)

| 배치 | 마스크 | 패킹 | 변화 |
|---:|---:|---:|---:|
| 1 | 1.82 | 2.18 | +19% |
| 2 | 3.53 | 4.25 | +21% |
| 5 | 5.65 | 9.49 | +68% |
| 10 | 11.36 | 15.39 | +36% |

```
마스크  배치 1 → 10   +523%
패킹    배치 1 → 10   +607%
```

이미 크게 이기던 조건에서도 더 좋아졌다. 문장당 디스크 읽기는 269.3 → 28.5로
여전히 배치 크기에 반비례한다. 실행 간 편차는 4%다.

배치 1에서도 +19%가 나온 점이 눈에 띈다. cold에서는 문장 하나짜리 묶음도
`padded`가 아니므로 경로가 바뀌지 않아야 하는데, 이 차이는 cold 측정의 변동
범위와 프로세스 시작 비용이 섞인 결과로 보인다. 단정하지 않는다.

### 길이가 균일한 입력 (경로 미변경 확인)

| 배치 | 변경 전 | 변경 후 |
|---:|---:|---:|
| 1 | 49.0 | 49.4 |
| 5 | 73.0 | 75.8 |
| 10 | 76.3 | 82.1 |

이 경로는 손대지 않았으므로 같아야 하고, 실제로 차이가 노이즈 범위다.

## 5. 이것이 M5 판정에 주는 의미

M5의 성능 수용 기준은 "+15% 이상 개선"이었다. 이전까지의 상황과 비교하면:

| 조건 | 이전 | 지금 |
|---|---:|---:|
| warm + 길이 편차 큼 | −28% (미달) | **+44% (통과)** |
| warm + 길이 균일 | +56% (통과) | +56% (유지) |
| cold | +523% (통과) | **+607% (통과)** |

**미달이던 유일한 조건이 해소됐다.** 정확도도 harrier 기준 원래 목표(1e-5)를
통과한다.

남은 것은 BERT다. 아직 마스크 경로를 쓰므로 최대 오차 2.345e-4가 그대로이고,
성능 이득도 받지 못한다. 같은 변경을 적용할 수 있으나 별도 작업이다.

---

## 6. 확인하지 못한 것

- **BERT에는 적용하지 않았다.** gemma3만 지원을 선언한 상태다.
- **다른 길이 분포와 다른 모델.** mixed_short와 harrier Q8 한 조합이다.
- **동시 요청 상황.** 모든 측정은 요청을 하나씩 순서대로 처리한 것이다.
- **묶음별 실제 토큰 수와 빈칸 비율**은 여전히 측정 결과로 노출되지 않는다.
  패킹의 이득이 입력 분포에 따라 어떻게 달라지는지 정량화하려면 이 값이 필요하다.

## 7. 재현

```sh
# 성능 (3회 반복, 배치 1 대조군이 41 근처인지 확인할 것)
docker run --rm --platform linux/arm64 \
  -v "$PWD":/src -v /tmp/nanoembed-m5-linux-build:/build \
  -v "$PWD/models":/models:ro -v /tmp/nanoembed-m5-cache:/cache \
  -v "$PWD/bench/results/M5-docker-desktop-arm64/per-sentence-attn":/out \
  nanoembed-linux-build:latest \
  bash -lc 'cd /src && NANOEMBED_CACHE_DIR=/cache python3 bench/runner.py \
    --milestone M5-PSA --scenarios bench/m5-per-sentence-attn.yaml \
    --bench /build/bin/nanoembed-bench --out /out/packed-run1.json'

# 메모리: 위에 --memory-profile --memory-profile-interval-ms 10 을 추가
```
