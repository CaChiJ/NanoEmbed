# M5 한눈에 보기: 여러 문장을 함께 임베딩하기

작성일: 2026-08-28

이 문서는 M5의 실제 배치(batch) 기능이 무엇인지, 어떤 상황에서 이득 또는 손해가
나는지, 그리고 아직 어떤 결정을 내려야 하는지를 요약한다. 구현 세부 사항이나 전체
측정값이 필요하면 문서 끝의 링크를 참고한다.

## 먼저 결론

- **기능 구현은 완료됐다.** `nanoembed_embed_batch`는 이제 문장을 하나씩 반복하는
  함수가 아니라, 여러 문장을 하나의 계산 그래프에 담아 처리한다.
- **효과는 입력과 캐시 상태에 따라 크게 달라진다.** 모델 파일을 디스크에서 읽어야
  하는 경우에는 배치 10이 배치 1보다 356~523% 높은 전체 처리량을 보였다. 반대로
  모델이 이미 메모리에 있고 문장 길이가 제각각이면 약 27% 느려졌다.
- **패딩이 성능 저하의 주된 원인이다.** 길이가 같은 문장만 사용한 대조 실험에서는
  같은 warm 조건에서도 배치 10이 56% 빨랐다.
- **패딩을 제거해 성능 문제가 해소됐다.** 어텐션을 문장별로 분리하고(정확도 오차 0),
  이어서 모든 토큰 단위 연산에서 패딩을 뺐다. warm·혼합 길이에서 배치 1 → 10이
  −28%에서 **+44%**로 바뀌었고, cold에서도 +523% → +607%가 됐다. 즉 M5의 성능
  기준을 못 넘던 유일한 조건이 해소됐다. 자세한 내용은
  [패딩 제거](m5-padding-removal.ko.md)에 있다. BERT에는 아직 적용하지 않았다.
- **M5를 기본 경로로 채택하기에는 아직 이르다.** 길이가 다른 문장을 함께 처리할 때
  원래의 정확도 기준을 넘지 못했고, 대표적인 warm·혼합 길이 조건의 성능 기준도
  충족하지 못했다. 기준을 바꿀지, 길이를 고려해 더 작은 배치로 나눌지 결정이 필요하다.

여기서 **warm**은 운영체제의 페이지 캐시에 모델 파일이 이미 올라와 있어 디스크
읽기가 일어나지 않는 상태이고, **cold**는 모델 파일을 처음 읽는 상태다.

## 1. M5가 해결하려 한 문제

NanoEmbed의 스트리밍 실행은 모델 전체를 메모리에 올려 두지 않는다. 필요한 레이어의
가중치만 파일에서 가져와 계산한 뒤 다음 레이어로 넘어간다. 큰 모델을 적은 메모리로
처리할 수 있다는 장점이 있다.

M4까지는 배치 API를 호출해도 내부에서는 문장을 하나씩 처리했다. 따라서 문장이
10개라면 각 레이어의 가중치를 10번 다시 읽었다.

```
기존:  문장 1의 전체 레이어 → 문장 2의 전체 레이어 → ...
       0층 읽기 → 1층 읽기 → ... → 0층 다시 읽기 → 1층 다시 읽기

M5:    0층 한 번 읽기 → 문장 여러 개의 0층 계산
       1층 한 번 읽기 → 문장 여러 개의 1층 계산
       ...
```

M5의 목표는 간단하다. **한 레이어를 읽었을 때 여러 문장이 함께 사용하게 하자.**
특히 모델 파일을 다시 읽어야 하는 상황에서 I/O를 줄이는 것이 목적이다.

문서에서 말하는 *sub-batch*는 한 요청을 실제로 나누어 처리하는 작은 문장 묶음이다.
한 묶음에는 최대 `max_batch`개가 들어간다. 예를 들어 문장이 23개이고
`max_batch=10`이면 10개·10개·3개의 sub-batch를 차례로 실행한다.

## 2. 실제 배치는 어떻게 동작하나

`nanoembed_embed_batch`의 공개 인터페이스는 그대로다. M5는 그 내부를 바꿔 여러
문장을 하나의 계산 그래프에서 처리하게 했다.

### 길이가 다른 문장의 길이를 맞춘다

한 번에 계산하는 텐서는 문장마다 같은 수의 토큰 칸을 가져야 한다. 따라서 한
sub-batch 안에서 가장 긴 문장을 기준으로 잡고, 짧은 문장의 뒤를 패딩(padding)으로
채운다.

```
문장 A (길이 4)   [ 토큰 토큰 토큰 토큰 패딩 패딩 ]
문장 B (길이 6)   [ 토큰 토큰 토큰 토큰 토큰 토큰 ]
```

패딩은 결과에 포함되면 안 되지만, 텐서의 한 칸이므로 계산 비용은 발생한다. 문장 길이
차이가 클수록 버리는 계산이 많아진다.

### 낭비를 줄이기 위해 길이순으로 정렬한다

처리 전에는 모든 문장을 토큰화하고 길이순으로 정렬한다. 비슷한 길이의 문장끼리 같은
sub-batch에 들어가므로 패딩을 줄일 수 있다. 계산이 끝난 뒤에는 원래 입력 순서로 결과를
되돌려 놓는다. 정렬은 내부 최적화일 뿐, API 사용자가 보는 결과 순서는 변하지 않는다.

### 패딩이 결과에 섞이지 않도록 제외한다

패딩이 있는 sub-batch에서는 다음 두 처리가 필요하다.

- **어텐션 마스크:** 실제 토큰이 패딩 위치를 참조하지 못하게 한다.
- **풀링 보정:** 토큰들의 평균이나 마지막 토큰으로 문장 벡터를 만들 때, 패딩을
  제외하고 실제 토큰만 사용한다.

sub-batch 안의 문장 길이가 모두 같으면 패딩과 마스크가 아예 필요 없다. 이때는 M4의
단일 문장 경로와 같은 형태의 그래프를 사용하며, 순차 실행 결과와 **정확히 동일하다**.

> 자세한 구현: [M5 구현 해설](m5-implementation-explained.ko.md)

## 3. 정확도와 안정성

### 결과는 얼마나 같은가

| 입력 구성 | 순차 실행과의 차이 |
|---|---|
| 같은 길이만 있는 sub-batch | **차이 0** — 완전히 동일 |
| 길이가 섞여 패딩·마스크를 사용한 sub-batch | 코사인 유사도 0.999998 이상, 최대 절대 오차 2.3e-4 |

패딩이 있는 그래프는 연산 형태와 부동소수점 덧셈 순서가 달라 아주 작은 차이가 생긴다.
코사인 유사도는 1.0에 가까울수록 두 벡터의 방향이 같다는 뜻이다. 현재 관측값은
실용적으로 매우 가깝지만, M5의 원래 정확도 기준(최대 절대 오차 1e-5)은 통과하지
못했다. 회귀 테스트는 관측값을 반영한 완화 기준을 사용하지만, 그 완화를 공식 호환성
기준으로 승인할지는 아직 결정되지 않았다.

### 확인한 동작

여기서 “실제 배치”란 문장을 하나씩 반복 호출하지 않고, 둘 이상의 문장을 한 계산
그래프에 넣어 함께 처리한다는 뜻이다. `eager`는 전체 계산을 한 그래프로 실행하는
경로이고, `streaming`은 레이어 단위로 가중치를 읽어 실행하는 경로다.

- eager와 streaming 실행 모두에서 실제 B>1 그래프가 동작한다.
- 결과는 항상 입력 순서대로 반환된다.
- 서로 다른 컨텍스트의 동시 배치 실행을 검증했다.
- 잘못된 입력과 할당 실패 경로에서 API의 오류 처리 계약을 검사했다.

다만 장시간 반복 실행(10,000회 soak)과 일부 추가 메모리 할당 실패 시나리오는 아직
측정·검증 과제로 남아 있다.

## 4. 측정 결과: 언제 이득이고 언제 손해인가

아래 수치는 `harrier-270m` Q8_0 모델, 문장 132개, 스레드 4개, 배치 크기 10 기준이다.
warm 수치는 기본 분할 전략인 `layer`에서 측정했고, cold 수치는 네 가지 분할 전략에서
관측된 범위다. 각 값은 세 번 실행한 중앙값이다. cold 처리량에는 모델 로드와 컨텍스트
생성 시간이 포함된다. 결과는 이 측정 환경과 코퍼스에 한정되며, 모든 모델과 장비에
그대로 일반화할 수는 없다.

| 조건 | 배치 1 대비 배치 10 | 해석 |
|---|---:|---|
| warm + 문장 길이 제각각 | **−27%** | 느려짐 |
| warm + 문장 길이 동일 | **+56%** | 빨라짐 |
| cold (모델 파일을 처음 읽음) | **+356~523%** | 크게 빨라짐 |

cold 측정은 페이지 캐시를 비우고 새 프로세스를 실행하므로 실행 간 편차가 크다. 세 번의
실행에서 처리량 편차는 중앙값 20.2%, 최대 57.8%였다. 따라서 이 표는 “배치 1과 배치 10의
차이가 매우 크다”는 결론에는 충분하지만, 배치 4와 5처럼 가까운 조건의 우열을 판단하는
근거로는 쓰지 않는다.

### cold에서는 왜 빨라지나

M5가 줄이려던 비용이 실제로 있기 때문이다. 기본 `layer` 전략의 cold 측정에서 문장
하나당 모델 파일을 읽느라 발생한 **major fault**(운영체제가 디스크에서 모델 페이지를
읽어 온 횟수)는 배치 크기에 거의 반비례했다.

| 배치 크기 | 문장당 모델 페이지 읽기(major fault) |
|---:|---:|
| 1 | 263.7회 |
| 2 | 130.5회 |
| 5 | 53.0회 |
| 10 | 25.9회 |

배치 10에서는 배치 1의 약 10분의 1만 발생한다. 즉, 한 레이어의 가중치를 여러 문장이
공유하도록 만든 설계 자체는 의도대로 작동한다.

참고로 cold 조건에서 모델 로드와 컨텍스트 생성을 제외한 순수 추론 시간도 문장당
41~52% 줄었다. 전체 처리량의 큰 증가폭에는 준비 비용을 여러 문장이 나눠 갖는 효과도
함께 들어 있다.

> 전체 수치와 측정 방법: [배치 × 파티션 매트릭스](m5-batch-partition-matrix.ko.md)

## 5. warm·혼합 길이에서는 왜 느려지나

warm 상태에서는 모델 파일이 이미 메모리에 있으므로 줄일 디스크 읽기가 없다. 대신
배치에는 다음 비용이 남는다.

1. 짧은 문장의 패딩 칸도 계산한다.
2. 패딩을 무시하기 위한 어텐션 마스크와 풀링 보정 연산이 추가된다.

특히 어텐션은 문장 길이에 따라 비용이 빠르게 커진다. 짧은 문장과 긴 문장이 같은
sub-batch에 있으면, 짧은 문장도 긴 문장의 길이에 맞춘 계산을 수행한다.

원인을 확인하기 위해 같은 7개 단어의 순서만 바꾼 문장 132개로 별도 대조 실험을 했다.
단어 구성이 같으므로 토큰 수가 같고, 패딩만 없앴을 뿐 실행 조건은 같았다.

| 배치 크기 | 길이가 동일한 입력 | 길이가 제각각인 입력 |
|---:|---:|---:|
| 1 | 49.0 문장/초 | 41.4 문장/초 |
| 5 | 73.0 (**+49%**) | 36.5 (−12%) |
| 10 | 76.3 (**+56%**) | 30.0 (−28%) |

같은 길이의 입력에서는 배치 크기가 커져도 처리량이 계속 높아졌다. 즉, warm·혼합
길이에서의 성능 저하는 배치 자체가 아니라 **패딩 비용**으로 설명된다. 다만 이 결과가
모든 모델과 모든 길이 분포에 그대로 적용된다는 뜻은 아니며, 현재 측정 범위에서는
패딩이 원인이라는 점이 확인됐다는 뜻이다.

## 5.5. 패딩을 줄인 첫 변경: 문장별 어텐션

5절에서 원인이 패딩으로 확인됐으므로, 실제로 패딩 계산을 없애봤다.

### 무엇을 바꿨나

어텐션은 각 토큰이 문장 안의 모든 칸을 훑는 연산이다. 지금까지는 문장 여러 개를
한 번에 계산했다 — 가장 긴 문장 길이에 맞춘 점수판을 문장 수만큼 만들고, 패딩 칸은
마스크로 가렸다. 바꾼 뒤에는 문장마다 자기 길이로 따로 계산한다.

길이 4·7·12인 문장 3개라면:

```
전:  12×12 점수판 3장 = 432칸 계산 → 마스크로 223칸을 무효화
후:  4×4 + 7×7 + 12×12 = 209칸 계산 → 마스크 불필요
```

**ggml은 마스크된 칸을 건너뛰지 않는다.** 점수판은 마스크를 적용하기 전에 이미
만들어지고, softmax도 패딩 칸까지 전부 훑는다. 즉 마스크는 결과를 맞추기 위한
장치일 뿐 계산량을 줄이지 않는다. 미리 잘라야 실제로 계산을 안 한다.

이 경로는 아키텍처가 지원을 선언해야 켜진다. 현재 gemma3(harrier)만 사용하고
BERT는 기존 마스크 경로를 유지한다.

### 결과 1 — 정확도 기준을 충족했다

| 모델 | 변경 전 최대 오차 | 변경 후 |
|---|---:|---:|
| harrier F32 | 4.361e-5 | **0** |
| harrier Q8 | 2.98e-8 | **0** |
| BERT F16 | 2.345e-4 | 2.345e-4 (미변경) |

harrier는 길이가 제각각인 입력에서도 문장을 하나씩 처리한 결과와 **완전히 동일하다.**
3절에서 넘지 못했던 원래 기준(1e-5)을 통과한다.

원인은 덧셈 순서였다. 마스크가 있으면 softmax가 패딩 칸까지 훑는데, 그 칸들은
결과에 기여하지 않으면서 연산에는 포함된다. 문장별로 쪼개면 실제 길이만 계산하므로
순차 처리와 연산이 같아진다.

### 결과 2 — 성능은 절반만 개선됐다

warm·혼합 길이, layer 파티션, 3회 중앙값이다. 배치 1은 코드 경로가 바뀌지 않으므로
측정 오염을 판별하는 대조군으로 사용했다.

| 배치 크기 | 기존(마스크) | 문장별 | 변화 |
|---:|---:|---:|---:|
| 1 | 41.4 | 41.3 | −0% (대조군) |
| 2 | 40.6 | 43.5 | +7% |
| 4 | 38.3 | 42.6 | +11% |
| 10 | 30.0 | 35.4 | **+18%** |

배치가 클수록 이득이 크다. 패딩이 배치와 함께 늘어나기 때문이다. 다만 방향은
아직 바뀌지 않았다.

```
기존 경로:   배치 1 → 10   −28%
문장별 경로: 배치 1 → 10   −14%
```

### 남은 두 가지 — 이후 해결됨

1. **조립 비용이 새로 생겼다.** 문장별 결과를 다시 하나의 텐서로 되돌리기 위해
   패딩을 채워 이어 붙인다. 계산은 줄었지만 메모리 이동은 남는다.
2. **선형 변환과 FFN은 아직 패딩을 계산한다.** 이번 변경은 어텐션에만 적용됐다.
   전체 계산의 약 95%를 차지하는 이 연산들은 여전히 패딩을 포함해 실행된다.

두 항목 모두 다음 단계에서 해결됐다. 실제 토큰만 이어 붙인 배열을 쓰도록 바꾸자
배치 1 → 10이 **+44%**가 됐고, 되돌릴 패딩이 없으므로 1번의 조립 비용도 사라졌다.
[패딩 제거](m5-padding-removal.ko.md)에 측정과 구현이 정리되어 있다. 이 연산들은 토큰 하나를 입력받아 토큰 하나를 출력할 뿐이므로
문장 경계를 알 필요가 없다. 따라서 패딩을 빼고 실제 토큰만 이어서 계산해도 결과가
같다. 문장 간 간섭이 가능한 유일한 연산인 어텐션은 이미 분리했으므로 안전하다.

## 6. 현재 판단과 다음 결정

M5는 “실제 배치 기능을 구현한다”는 목표는 달성했다. 하지만 “기본 경로로 배포해도
항상 성능·정확도 기준을 만족한다”는 결론에는 도달하지 못했다.

M5의 원래 수용 기준 중 관련 결과는 다음과 같다.

| 기준 | 현재 결과 |
|---|---|
| 실제 배치 실행, 결과 순서 복원, streaming 동작 | 통과 |
| 서로 다른 컨텍스트의 동시 실행 | 통과 |
| 원래 정확도 기준: cosine ≥ 0.999999, 최대 절대 오차 ≤ 1e-5 | 패딩 경로에서 미달 |
| warm·혼합 길이에서 배치 성능 +15% 이상 | 미달 (배치 10에서 약 −27%) |

현재 `max_batch`는 sub-batch를 나누는 **유일한 기준**이다. 사용자가 `max_batch=10`을
주면 내부적으로도 항상 최대 10개씩 처리한다. 길이 차이가 큰 경우 자동으로 더 작게
나누는 숨은 규칙은 넣지 않았다. 그런 규칙은 성능 문제를 완화할 수 있지만, API의
동작과 벤치마크 결과를 예측하기 어렵게 만들기 때문이다.

따라서 다음 세 가지를 명시적으로 결정해야 한다.

| 결정 항목 | 선택이 필요한 이유 |
|---|---|
| 길이를 고려한 분할 정책 | 패딩을 줄일 수 있지만, 현재 `max_batch` 계약을 확장한다. |
| 정확도 기준 | 패딩 경로의 허용 오차를 공식적으로 완화할지 결정해야 한다. |
| 기본 경로 채택 여부 | warm·혼합 길이 성능 기준을 충족한 뒤 기본값으로 삼는 것이 안전하다. |

이 결정 전에는 M5를 기능 구현 완료로 보되, 모든 환경에서의 성능 개선 또는 기본 경로
승인으로 해석하지 않는다.

## 7. 추가로 확인한 점

### 그래프 분할 방식

스트리밍 실행에서 모델을 어떤 단위로 그래프로 나눌지도 비교했다.

| 전략 | 관찰 결과 |
|---|---|
| `layer` (레이어 하나씩) | 현재 기본값. 가장 좋거나 사실상 동률 |
| `attn-ffn` (한 레이어를 둘로) | `layer`와 구분하기 어려움 |
| `budget:10M` (가중치 10 MiB 단위) | `layer`와 구분하기 어려움 |
| `unit` (가장 작은 실행 단위) | 속도 약 −15%, 메모리 최대 +173% |

`unit`이 불리한 이유는 그래프 경계가 늘어날수록 레이어 사이의 중간 결과를 저장하고
다시 읽는 작업이 많아지기 때문이다. 현재로서는 기본값 `layer`를 바꿀 근거가 없다.

### 배치 메모리는 RSS 최대값만으로 판단할 수 없다

측정한 조건에서는 최대 RSS가 모두 약 55 MiB로 거의 같았다. RSS는 프로세스가 매핑한
메모리의 총량이라, 모델 파일을 메모리에 매핑하는 비용의 영향을 크게 받는다. 그래서
계산 중 배치가 추가로 쓰는 메모리를 잘 보여 주지 않는다.

배치의 영향을 보려면 PSS 또는 USS도 함께 봐야 한다. PSS는 공유 메모리를 프로세스마다
나누어 계산한 값이고, USS는 해당 프로세스만 사용하는 메모리다. 예를 들어 `layer`
전략의 PSS 평균은 배치 1에서 18.3 MiB, 배치 10에서 34.4 MiB로 증가했다.

또한 배치 크기와 메모리 사용량이 항상 비례하지는 않았다. 길이순 정렬 뒤 마지막
sub-batch에 가장 긴 문장들이 모이고, 마지막 묶음의 크기가 배치 크기에 따라 달라지기
때문으로 추정된다. 이 설명은 아직 검증되지 않았으며, sub-batch별 실제 토큰 수와
패딩 수를 결과에 기록해야 확정할 수 있다.

## 8. 아직 확인하지 못한 것

- **sub-batch별 토큰 수와 패딩 수:** 내부에서는 계산하지만, 벤치마크 결과에는 아직
  기록하지 않는다. 이 정보가 있어야 위 메모리 현상과 입력 길이 분포를 정확히 분석할
  수 있다.
- **여러 요청이 동시에 들어오는 부하:** 서로 다른 컨텍스트의 동시 실행 안전성은
  검증했지만, 서버처럼 여러 요청이 경쟁하는 조건의 성능은 측정하지 않았다.
- **중간 정도의 길이 편차:** 현재는 길이가 완전히 같은 입력과 차이가 큰 입력만 비교했다.
  어느 지점부터 패딩 비용이 이득보다 커지는지는 알 수 없다.
- **다른 모델과 장비:** 수치는 Docker Desktop arm64의 `harrier-270m` Q8_0 조합에서
  얻었다. 다른 모델, 양자화 방식, CPU에서는 별도 측정이 필요하다.
