# M5 최종 보고서: 여러 문장을 실제 배치로 처리하기

작성: 2026-08-28 · 종료: 2026-08-31

이 문서는 M5의 설계, 용어, 구현, 정확도, 성능·메모리 측정과 최종 결정을 한곳에
정리한 정본이다. 통합 전 세부 문서들은 Git 커밋 `5c8944b`에서 그대로 볼 수 있다.

## 결론

- M5는 `nanoembed_embed_batch`가 여러 문장을 한 그래프에서 처리하도록 구현됐다.
  M4처럼 문장마다 모든 레이어를 다시 읽는 방식이 아니다.
- Harrier의 기본 설정은 **`A문장별/F패킹/N패킹/P레이어`**다. 특정 입력 분포와
  kernel에서 dense 연산이 더 유리한 경우를 위해 기존
  `A패딩마스크/F패딩/N패딩` 경로도 명시적 옵션으로 유지한다.
- 홈서버 warm·혼합 길이 입력에서 최종 설정의 처리량은 배치 1의 45.52문장/초에서
  배치 10의 69.15문장/초로 **51.9% 증가**했다. 배치 10에서 이미 배치 128
  처리량의 약 95%에 도달했다.
- 최종 설정의 배치 64 처리량은 기존 패딩 방식보다 **156% 높았고**, PSS는
  119.81 MiB에서 62.57 MiB로 줄었다.
- 스트리밍 파티션은 `layer`가 기본값으로 적합하다. `attn-ffn`은 처리량 차이를
  구분할 수 없었고, `unit`은 모든 배치에서 4.5~8.4% 느리며 큰 배치에서 메모리도
  더 사용했다.
- Harrier는 문장을 하나씩 처리한 결과와 정확히 같아졌다. BERT는 아직 기존 패딩
  마스크 경로를 사용하므로 M5의 패킹 성능·정확도 개선 범위에 포함하지 않는다.

## 1. 설정 이름과 꼭 필요한 용어

설정 이름은 `A(어텐션)/F(FFN)/N(Norm)/P(스트리밍 파티션)` 순서다. 이름만 보고
실행 구성을 알 수 있도록 네 축을 모두 적는다.

길이 4·7·12인 문장을 함께 처리하는 예를 보자. `●`는 실제 토큰, `·`는 결과에서
버릴 패딩이다.

```text
패딩:  36칸
●●●●········
●●●●●●●·····
●●●●●●●●●●●●

패킹:  23칸
●●●●|●●●●●●●|●●●●●●●●●●●●
      문장 경계는 offsets에 기록
```

| 축과 옵션 | 뜻 | 위 예시의 계산 범위 |
|---|---|---:|
| `A패딩마스크` | 길이 12인 점수판을 문장마다 만들고 빈 key를 `-∞`로 가린다 | 12² × 3 = 432칸 |
| `A문장별` | 문장 경계에서 잘라 실제 길이만 어텐션한다 | 4² + 7² + 12² = 209칸 |
| `F패딩`, `N패딩` | FFN·Norm이 직사각형의 패딩까지 처리한다 | 각각 36토큰 |
| `F패킹`, `N패킹` | FFN·Norm이 이어 붙인 실제 토큰만 처리한다 | 각각 23토큰 |
| `P레이어` (`layer`) | 레이어 전체를 그래프 하나로 실행한다 | 레이어당 1그래프 |
| `P어텐션-FFN` (`attn-ffn`) | 어텐션과 FFN을 나눈다 | 레이어당 2그래프 |
| `P유닛` (`unit`) | norm, QKV, core 등 실행 유닛마다 나눈다 | Harrier는 레이어당 8그래프 |
| `P예산10M` (`budget:10M`) | 가중치 합이 10 MiB를 넘기 전까지 유닛을 묶는다 | Harrier Q8에서는 `layer`와 같음 |

패딩 마스크는 빈칸이 정답에 섞이는 것만 막는다. ggml이 가려진 칸의 행렬곱과
softmax를 건너뛰는 것은 아니므로 계산량은 줄지 않는다. Harrier의 causal mask는
미래 토큰을 막는 별도 장치이며 두 A 옵션 모두에 적용된다.

형식상 조합은 A 2개 × F 2개 × N 2개 × P 4개 = 32개다. 다만 다음 이유로 32개를
모두 측정하지 않았다.

- 현재 구현은 `A패딩마스크/F패딩/N패딩`과
  `A문장별/F패딩/N패딩`, `A문장별/F패킹/N패킹` 세 A·F·N 조합만 제공한다.
- F와 N만 따로 패킹하는 중간 조합은 패딩·패킹 배열 간 변환이 필요하지만 구현하지
  않았다.
- Harrier Q8의 한 레이어는 10 MiB보다 작아 `budget:10M`과 `layer`의 실제
  그래프 구성이 같다.

따라서 먼저 `P레이어`에서 구현된 A·F·N 세 조합을 비교하고, 그 승자인
`A문장별/F패킹/N패킹`을 고정해 서로 다른 P 세 개를 비교했다.

## 2. M5가 바꾼 실행 방식

M4의 배치 API는 내부에서 문장을 하나씩 실행했다. 문장 10개라면 같은 레이어
가중치를 10번 다시 읽었다. M5는 한 레이어를 읽었을 때 sub-batch의 여러 문장이
함께 사용한다.

```text
M4: 문장 1의 0~N층 → 문장 2의 0~N층 → ...
M5: 여러 문장의 0층 → 여러 문장의 1층 → ... → 여러 문장의 N층
```

sub-batch는 한 요청을 `max_batch`개 이하로 나눈 문장 묶음이다. 예를 들어 23문장을
`max_batch=10`으로 처리하면 10·10·3개 묶음이 된다. 공개 C API와 출력 순서는
기존 계약을 유지했고, layout 선택 함수만 additive하게 추가했다.

보편적인 최적 batch size는 없다. 처리량, PSS, 입력 길이 분포와 동시 요청 수의
우선순위가 사용자마다 다르므로 호출자가 `nanoembed_context_params.max_batch`를
설정한다. 라이브러리는 측정값을 근거로 5나 10 같은 값을 자동 선택하지 않는다.

최종 Harrier 경로는 다음 순서로 동작한다.

1. 문장을 모두 토큰화하고 길이순으로 정렬해 비슷한 길이끼리 묶는다.
2. 실제 토큰만 이어 붙이고 문장별 시작 위치를 기록한다.
3. 임베딩, Norm, Q·K·V·O 선형변환과 FFN은 이어 붙인 토큰 배열을 처리한다.
4. 어텐션만 문장 경계에서 잘라 각 문장의 실제 길이로 계산한다.
5. 풀링도 각 문장의 실제 구간만 사용하고 결과를 원래 입력 순서로 돌려놓는다.

문장 경계를 알아야 하는 연산은 어텐션과 풀링뿐이다. FFN과 Norm 같은 토큰 단위
연산은 다른 문장의 토큰을 이어 붙여도 서로 간섭하지 않는다. 길이가 모두 같은
묶음은 패딩이 없으므로 기존 직사각형 경로를 그대로 쓴다.

구현 중에는 임베딩과 FFN 그룹이 패킹 여부를 서로 다르게 판단하던 결함도 발견했다.
패킹은 개별 그룹이 아니라 sub-batch 전체의 성질로 정하고, 임베딩부터 최종 풀링까지
같은 값을 사용하도록 고쳤다.

주요 구현 위치는 다음과 같다.

| 영역 | 파일 |
|---|---|
| sub-batch와 패킹 배열 | [`src/batch.cpp`](../src/batch.cpp) |
| 문장별 어텐션 | [`src/forward/gqa_attention.cpp`](../src/forward/gqa_attention.cpp) |
| 문장별 풀링 | [`src/forward/pool.cpp`](../src/forward/pool.cpp) |
| eager 실행 | [`src/embedder.cpp`](../src/embedder.cpp) |
| streaming·파티션·경계 슬롯 | [`src/streaming_execution.cpp`](../src/streaming_execution.cpp) |
| Harrier 지원 선언 | [`src/arch/gemma3_arch.cpp`](../src/arch/gemma3_arch.cpp) |

## 3. 정확도와 안정성

초기 패딩 마스크 방식은 연산 모양과 덧셈 순서가 순차 실행과 달라 작은 오차가
생겼다. 문장별 어텐션은 실제 길이만 계산해 순차 실행과 연산을 같게 만들었다.

| 모델 | 패딩 마스크 최대 절대 오차 | 문장별 어텐션 이후 |
|---|---:|---:|
| Harrier F32 | 4.361e-5 | **0** |
| Harrier Q8 | 2.98e-8 | **0** |
| BERT F16 | 2.345e-4 | 미적용, 기존 값 유지 |

다음 동작도 회귀 테스트로 확인했다.

- eager와 streaming 모두 실제 B>1 그래프를 실행한다.
- 배치 결과는 입력 순서대로 반환된다.
- 서로 다른 컨텍스트의 동시 배치 실행이 안전하다.
- 그래프 생성 실패 시 residency lease와 출력이 계약대로 정리되고 같은 컨텍스트를
  다시 사용할 수 있다.
- 홈서버 Release 구성에서 필수 모델 검사를 포함한 등록 테스트 34개가 통과했다.
  선택 사항인 Q4 모델이 없어 report-only 검사 2개는 등록되지 않았다.
- 배치 128도 세 번 모두 완료됐으며 이전 Docker Desktop 중단은 홈서버에서
  재현되지 않았다.

10,000회 장시간 soak와 모든 host/backend 할당 실패 지점의 주입 검사는 M5 범위에서
수행하지 않았다.

## 4. 측정 범위와 읽는 법

최종 판정은 다음 홈서버 측정을 우선한다.

| 항목 | 값 |
|---|---|
| CPU·OS | AMD Ryzen 5 5600G, Linux x86_64, 커널 6.8.0-138 |
| 빌드 | Release, GCC 13.3, ggml `387fa29f` |
| 모델 | harrier-270m Q8_0 |
| 입력 | `mixed_short` 132문장 |
| 실행 | streaming, 스레드 4개, warm 캐시 |
| 반복 | 각 셀 독립 실행 3회, 중앙값 |
| 성능 | 메모리 상세 관측을 끈 profile-off |
| 메모리 | 10 ms 간격 profile-on, 유효 표본 100% |
| 측정 기준 revision | `6961bbf` |
| 측정 바이너리 SHA-256 | `ae9264c16e10c4e2b5841fc66d4c4f60eaf39c6d43896db9497a6869d46ad717` |

PSS는 공유 파일 페이지를 프로세스 수로 나눠 더한 값이라 프로세스가 실제 부담하는
메모리를 비교하는 데 사용했다. `PSS file`은 모델 mmap과 라이브러리 같은 파일 기반
페이지, `PSS anon`은 활성값·계산 버퍼 같은 익명 메모리다.

`/proc/<pid>/smaps_rollup` 관측은 실행을 방해할 수 있어 profile-on 지연시간을 성능
판정에 사용하지 않았다. 서로 다른 머신의 절대값도 직접 비교하지 않았다. 초기
Docker Desktop arm64 결과는 문제 발견과 방향 확인에, 홈서버 x86_64 결과는 최종
비교에 사용했다.

## 5. 초기 결과: 실제 배치는 됐지만 패딩이 비쌌다

초기 `A패딩마스크/F패딩/N패딩` 측정은 입력과 캐시 상태에 따라 방향이 달랐다.

| 조건 | 배치 1 → 10 | 해석 |
|---|---:|---|
| warm, 길이가 제각각 | 약 **−28%** | 패딩 계산이 가중치 재사용 이득보다 큼 |
| warm, 길이가 동일 | **+56%** | 패딩이 없으면 실제 배치가 이득 |
| cold, 길이가 제각각 | **+356~523%** | 모델 페이지 읽기를 여러 문장이 공유 |

기본 `layer`의 cold 측정에서 문장당 major fault는 배치 1의 263.7회에서 배치 10의
25.9회로 약 10분의 1이 됐다. 즉 레이어 가중치를 여러 문장이 공유한다는 M5의
기본 설계는 의도대로 동작했고, warm·혼합 길이의 문제는 배치 자체가 아니라 패딩이었다.

## 6. A·F·N 비교: 패킹이 병목을 제거했다

P는 `layer`로 고정했다. 처리량은 문장/초이며 각 셀은 세 독립 실행의 중앙값이다.

| 배치 | `A패딩마스크/F패딩/N패딩` | `A문장별/F패딩/N패딩` | `A문장별/F패킹/N패킹` | 최종 vs 기존 |
|---:|---:|---:|---:|---:|
| 1 | 45.72 | 45.53 | 45.52 | −0.4% |
| 2 | 48.46 | 48.58 | 56.46 | +16.5% |
| 5 | 43.82 | 44.96 | 65.71 | +50.0% |
| 10 | 38.57 | 38.99 | 69.15 | +79.3% |
| 16 | 34.84 | 35.75 | 69.76 | +100.2% |
| 32 | 30.78 | 31.71 | 71.64 | +132.8% |
| 64 | 28.12 | 28.80 | 72.04 | **+156.2%** |

A만 문장별로 바꾼 차이는 배치 2~64에서 0.3~3.0%였고 기존 방식의 실행 범위가
최대 11.0%여서 홈서버에서는 성능 차이를 구분할 수 없었다. 정확도는 해결했지만
대부분의 토큰 단위 연산이 여전히 패딩을 계산했기 때문이다. F·N뿐 아니라 임베딩,
선형변환과 풀링까지 실제 토큰만 처리하자 차이가 실행 편차보다 크게 벌어졌다.

메모리도 같은 방향이었다. 아래는 PSS 평균이다.

| 배치 | `A패딩마스크/F패딩/N패딩` | `A문장별/F패딩/N패딩` | `A문장별/F패킹/N패킹` |
|---:|---:|---:|---:|
| 1 | 46.93 | 46.83 | 46.89 |
| 2 | 36.97 | 36.95 | 36.94 |
| 5 | 43.52 | 43.55 | 37.06 |
| 10 | 57.17 | 57.16 | 43.44 |
| 16 | 69.79 | 69.89 | 47.81 |
| 32 | 79.45 | 79.50 | 48.87 |
| 64 | 119.81 | 119.91 | **62.57** |

최종 설정의 처리량은 배치 10부터 거의 포화했다. 별도 배치 128 측정의 중앙값은
72.91문장/초였고 배치 10은 그 약 95%였다. 32·64·128의 차이는 실행 범위와 겹쳐
우열을 구분하기 어렵다.

cold에서도 최종 설정이 큰 배치에서 앞섰다.

| 배치 | 기존 패딩 방식 | 최종 패킹 방식 | 차이 |
|---:|---:|---:|---:|
| 1 | 2.18 | 2.21 | +1.4% |
| 2 | 4.26 | 4.34 | +1.9% |
| 3 | 6.17 | 6.41 | +4.0% |
| 4 | 7.82 | 8.37 | +6.9% |
| 5 | 9.17 | 9.96 | +8.6% |
| 10 | 14.10 | 17.08 | **+21.2%** |

문장별 어텐션 결과를 합치는 구현도 비교했다. 배치 1로 정규화한 배치 64 처리량은
왼쪽부터 이어 붙이기 1.494배, 짝을 지어 붙이기 1.579배, 현재 제자리 쓰기 1.584배였다.
왼쪽 방식의 큰 배치 저하는 줄었지만, 짝 접기와 제자리 쓰기의 차이는 측정 편차보다
작아 성능 우열을 말할 수 없다.

## 7. 최종 P 비교: `layer`를 유지한다

A·F·N을 최종 `A문장별/F패킹/N패킹`으로 고정하고 P만 바꿨다. `budget:10M`은
이 Q8 모델에서 `layer`와 같은 그룹이므로 제외했다.

### 처리량

단위는 문장/초다. 괄호는 같은 배치의 `P레이어` 대비 변화다.

| 배치 | `P레이어` | `P어텐션-FFN` | `P유닛` |
|---:|---:|---:|---:|
| 1 | 44.25 | 43.11 (−2.6%) | 40.51 (−8.4%) |
| 2 | 54.72 | 54.19 (−1.0%) | 51.61 (−5.7%) |
| 5 | 64.48 | 63.88 (−0.9%) | 61.42 (−4.7%) |
| 10 | 69.15 | 68.66 (−0.7%) | 66.05 (−4.5%) |
| 16 | 70.26 | 70.05 (−0.3%) | 66.72 (−5.0%) |
| 32 | 71.65 | 71.13 (−0.7%) | 67.25 (−6.1%) |
| 64 | 71.90 | 71.53 (−0.5%) | 66.79 (−7.1%) |

동일 셀의 처리량 실행 범위는 중앙값 0.8%, 최대 2.1%였다. 따라서 배치 2~64에서
0.3~1.0% 차이인 `layer`와 `attn-ffn`의 우열은 구분할 수 없다. `unit`의 손해는
최소 4.5%이고 모든 배치에서 반복돼 실제 손해로 판단한다. 문장당 p99 지연시간도
배치 64에서 `layer` 22.03 ms, `unit` 23.81 ms로 `unit`이 8.0% 길었다.

### 전체 PSS

단위는 MiB다.

| 배치 | `P레이어` | `P어텐션-FFN` | `P유닛` |
|---:|---:|---:|---:|
| 1 | 46.87 | 46.63 | 47.63 |
| 2 | 47.13 | 46.82 | 47.82 |
| 5 | 37.05 | 39.27 | 42.37 |
| 10 | 43.41 | 43.55 | 48.44 |
| 16 | 47.67 | 44.08 | 51.47 |
| 32 | 48.91 | 49.51 | 61.05 |
| 64 | 62.54 | 64.40 | **89.95** |

`attn-ffn`은 배치에 따라 `layer`보다 높기도 낮기도 해 일관된 메모리 우위가 없다.
`unit`은 배치 5 이상에서 항상 크고 배치 32·64에서 차이가 급격히 벌어졌다.

### 왜 `unit`이 가장 작지 않은가

`unit`이 이론적으로 최소화하는 것은 전체 PSS가 아니라 **동시에 임대하는 가중치
범위**다. 파티션 진단은 예상대로 움직였다.

| P | 최대 그룹 가중치 | `layer` 대비 |
|---|---:|---:|
| `layer` | 5,792 KiB | — |
| `attn-ffn` | 4,085 KiB | −29.5% |
| `unit` | **2,720 KiB** | −53.0% |

하지만 그래프를 나누면 그래프 안에서 바로 소비되던 중간값이 경계를 넘어야 한다.
현재 `SlotStore`는 `x`, `xn`, `q`, `k`, `v`, `h`, `x1`, `fn`, `fh`, `fd` 같은
경계값을 F32 호스트 버퍼에 내려받고 다음 그래프에 다시 올린다. 각 슬롯의 버퍼는
재사용을 위해 한 번 커진 용량을 줄이지 않는다. 이 비용은 실제 토큰 수와 함께
커지지만 한 레이어에서 줄일 수 있는 가중치 양은 일정하다.

배치 64의 PSS 분해가 이 설명과 일치한다.

| P | 전체 PSS | 익명 메모리 | 파일 메모리 |
|---|---:|---:|---:|
| `layer` | 62.54 | 34.05 | 28.49 |
| `attn-ffn` | 64.40 | 36.21 | 28.19 |
| `unit` | 89.95 | **60.94** | 29.02 |

`unit`과 `layer`의 파일 메모리는 0.53 MiB 차이뿐이지만 익명 메모리는 26.89 MiB
차이다. 세 반복 모두 warmup 직후부터 종료까지 이 익명 메모리가 거의 같은 값으로
유지돼 일시적인 표본 착시도 아니다. `madvise(DONTNEED)`는 즉시 회수를 보장하는
명령이 아니라 커널에 주는 힌트이므로, 임대 범위 감소가 warm 실행의 파일 PSS 감소로
그대로 나타나지도 않았다.

따라서 “가중치 임대량은 `unit`이 최소”와 “현재 구현의 전체 메모리는 `unit`이
최대”는 모순이 아니다. 이번 조건에서는 약 3 MiB의 가중치 절감 가능성보다 약
27 MiB의 경계 버퍼 증가가 훨씬 컸다.

## 8. M5 종료 결정

Harrier의 M5 기본 구성은 다음과 같이 확정한다.

| 축 | 선택 | 이유 |
|---|---|---|
| A | `문장별` | 패딩 어텐션을 없애고 순차 실행과 정확히 같음 |
| F | `패킹` | 실제 토큰만 처리해 큰 배치의 FFN 낭비 제거 |
| N | `패킹` | 실제 토큰만 처리해 활성값과 계산량 감소 |
| P | `layer` | `attn-ffn`과 사실상 동률이며 `unit`보다 빠르고 메모리가 작음 |

공개 API에서 아무 설정도 바꾸지 않으면 위 최적화 layout을 사용한다. 호출자는
`nanoembed_context_set_batch_layout(ctx, NANOEMBED_BATCH_LAYOUT_PADDED)`로 unequal-length
batch에 right padding, padding attention mask와 padded token-wise 연산을 강제할 수
있다. 다시 `NANOEMBED_BATCH_LAYOUT_DEFAULT`를 설정하면 기본 경로로 돌아온다. 이
선택은 frozen `nanoembed_context_params`의 크기와 기존 필드 offset을 바꾸지 않는다.

이 `mixed_short` 조건에서는 처리량 위주라면 배치 10이 실용적인 시작점이었다. 이는
라이브러리 기본값이나 자동 튜닝 규칙이 아니다. 호출자가 입력당 지연시간, PSS,
입력 길이 분포와 운영 동시성 요구에 맞춰 `max_batch`를 선택한다.

`max_batch`를 고르는 사람에게 필요한 것은 처리량 곡선만이 아니므로, 위
`P레이어` 측정에서 처리량을 전체 PSS로 나눈 값을 함께 남긴다. 단위는
문장/초/MiB이고 두 열 모두 같은 표의 중앙값이다.

| 배치 | 처리량 | PSS | 처리량/PSS |
|---:|---:|---:|---:|
| 1 | 44.25 | 46.87 | 0.94 |
| 2 | 54.72 | 47.13 | 1.16 |
| 5 | 64.48 | 37.05 | **1.74** |
| 10 | 69.15 | 43.41 | 1.59 |
| 16 | 70.26 | 47.67 | 1.47 |
| 32 | 71.65 | 48.91 | 1.46 |
| 64 | 71.90 | 62.54 | 1.15 |

처리량만 보면 큰 배치가 계속 유리하지만 메모리당 처리량은 단조롭지 않다. 배치
10 이후 처리량은 거의 포화하는데 활성값과 경계 버퍼는 계속 커지므로 비율이 다시
떨어진다. 즉 메모리가 빠듯한 배포에서는 배치 5~10, 처리량이 최우선이면 배치
16 이상이 합리적인 출발점이다. 다만 배치 5의 PSS 하락은 세 반복에서 모두
재현됐지만 원인을 확정하지 못했다. 길이 정렬 후 마지막 sub-batch 모양, 패킹된
그래프의 replan, allocator high-water 중 무엇이 지배적인지는 sub-batch별 실제
토큰 수와 replan 수를 벤치 JSON에 노출한 뒤에야 말할 수 있다. 그 전까지 이
비율표는 경향 참고용이며 운영 기본값의 근거로 쓰지 않는다.

M5 이후 메모리 절감은 새 단계에서 다룬다. 우선순위는 다음과 같다.

1. 벤치 결과에 `advised_bytes_high_water`, `slot_resident_bytes`, 활성값 복사량과
   graph replan 수를 직접 노출한다.
2. `SlotStore`를 슬롯별 영구 최대 용량 대신 생존 구간을 고려한 공유 arena로 바꾼다.
3. 그래프 경계의 호스트 왕복을 없애거나 재사용 가능한 backend 버퍼로 넘긴다.
4. 가중치 절감과 경계 활성값 비용을 함께 계산하는 하이브리드 파티션을 검토한다.

## 9. 한계

- 최종 A·F·N 및 P 비교는 한 x86_64 머신, Harrier Q8, `mixed_short`, 요청을 하나씩
  처리하는 조건이다. 다른 CPU·모델·길이 분포와 동시 요청에 그대로 일반화하지 않는다.
- BERT는 문장별 어텐션과 패킹을 아직 지원하지 않는다.
- cold 비교는 최종 P 세 방식까지 확장하지 않았다.
- 묶음별 실제 토큰 수·패딩 비율과 내부 slot/lease 진단은 벤치 JSON에 아직 나오지
  않는다.
- profile-on 측정은 메모리 관측용이며 그 실행의 지연시간은 성능 수치가 아니다.
- 홈서버에는 상시 작업이 있어 1% 안팎의 차이는 결론으로 사용하지 않았다.
