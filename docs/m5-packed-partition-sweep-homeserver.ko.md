# M5 최종 패킹 × 스트리밍 파티션 비교

작성일: 2026-08-30

## 결론

`A문장별/F패킹/N패킹`을 고정하고 P만 바꿔 측정했다.

- **기본값은 `P레이어`가 맞다.** 배치 2~64에서 `P어텐션-FFN`은 처리량이
  `P레이어`보다 0.3~1.0% 낮았다. 셀별 실행 범위가 최대 2.1%라 둘의 성능 차이는
  구분할 수 없다.
- **`P유닛`은 제외해도 된다.** 모든 배치에서 `P레이어`보다 4.5~8.4% 느렸고,
  p99 지연시간도 3.0~8.0% 길었다.
- `P유닛`의 메모리 손해는 배치가 클수록 커졌다. 배치 64의 PSS 평균은
  `P레이어` 62.54 MiB, `P유닛` 89.95 MiB로 **43.8% 차이**였다.
- 세 P 모두 배치 10부터 처리량이 거의 포화했다. `P레이어` 배치 10은
  69.15문장/초로 배치 64의 96%를 냈다.

따라서 이 조건의 선택은 **`A문장별/F패킹/N패킹/P레이어`**다.

## 무엇을 바꿨나

A·F·N은 그대로 두고 P만 바꿨다.

| 축 | 고정값 |
|---|---|
| A: 어텐션 | 문장별 실제 길이 |
| F: FFN | 실제 토큰 패킹 |
| N: Norm | 실제 토큰 패킹 |

P는 한 레이어를 몇 개의 그래프로 나눌지 정한다.

```text
P레이어       [ 어텐션 + FFN 전체 ]
P어텐션-FFN   [ 어텐션 ] → [ FFN ]
P유닛         [norm] → [qkv] → [core] → ... → [ffn_down] → [post]
```

| P 설정 이름 | 실행 옵션 | 레이어당 그래프 | 의미 |
|---|---|---:|---|
| `P레이어` | `layer` | 1 | 레이어 전체를 한 번에 실행 |
| `P어텐션-FFN` | `attn-ffn` | 2 | 어텐션과 FFN 경계에서 분리 |
| `P유닛` | `unit` | 8 | 각 실행 유닛을 따로 실행 |

그래프 경계가 늘면 한 번에 잡아 두는 가중치는 줄 수 있지만, 중간 활성값을 호스트의
`SlotStore`에 저장했다가 다음 그래프로 다시 읽는 비용이 생긴다.

`budget:10M`은 제외했다. Harrier Q8 한 레이어의 가중치는 약 5.7 MiB라 10 MiB
예산 안에 전부 들어가며, 이 모델에서는 `layer`와 같은 그룹을 만든다.

## 측정 방법

| 항목 | 값 |
|---|---|
| 환경 | AMD Ryzen 5 5600G, Linux x86_64, 논리 CPU 12개 |
| 모델 | harrier-270m Q8_0 |
| 입력 | `mixed_short` 132문장 |
| 실행 | warm, streaming, 스레드 4개 |
| 배치 | 1·2·5·10·16·32·64 |
| 격자 | 배치 7 × P 3 = 21셀 |
| 반복 | 각 셀 독립 실행 3회, 중앙값 사용 |
| 성능 | 메모리 상세 관측을 끈 profile-off 3회 |
| 메모리 | 10ms 간격 profile-on 3회, PSS·USS·RSS 표본 유효 비율 100% |
| Git revision | `6961bbf` |

성능과 메모리를 분리한 이유는 `/proc` 메모리 관측 자체가 실행을 방해할 수 있기
때문이다. profile-on의 지연시간은 성능 수치로 사용하지 않았다.

세 성능 실행에서 동일 셀의 처리량 범위는 중앙값 0.8%, 최대 2.1%였다. 21셀 전체
평균 처리량도 실행별 62.31·62.34·62.45문장/초로 안정적이었다. 메모리 PSS 평균의
실행 범위는 중앙값 0.19%, 최대 0.43%였다.

## 성능 결과

처리량은 문장/초이며 높을수록 좋다. 괄호는 `P레이어` 대비 변화다.

| 배치 | `P레이어` | `P어텐션-FFN` | `P유닛` |
|---:|---:|---:|---:|
| 1 | 44.25 | 43.11 (-2.6%) | 40.51 (-8.4%) |
| 2 | 54.72 | 54.19 (-1.0%) | 51.61 (-5.7%) |
| 5 | 64.48 | 63.88 (-0.9%) | 61.42 (-4.7%) |
| 10 | 69.15 | 68.66 (-0.7%) | 66.05 (-4.5%) |
| 16 | 70.26 | 70.05 (-0.3%) | 66.72 (-5.0%) |
| 32 | 71.65 | 71.13 (-0.7%) | 67.25 (-6.1%) |
| 64 | 71.90 | 71.53 (-0.5%) | 66.79 (-7.1%) |

`P레이어`와 `P어텐션-FFN`의 배치 2~64 차이는 최대 1.0%로 실행 범위보다 작다.
`P어텐션-FFN`이 더 빠르다고 볼 근거도, 의미 있게 느리다고 볼 근거도 없다.

`P유닛`은 일곱 배치 모두 느렸다. 차이의 최솟값도 4.5%라 최대 실행 범위 2.1%보다
크고, 배치 전 구간에서 같은 방향이므로 실제 손해로 판단한다.

### 긴 꼬리 지연시간

문장당 p99 지연시간은 ms이며 낮을수록 좋다. 대표 배치만 표시했다.

| 배치 | `P레이어` | `P어텐션-FFN` | `P유닛` |
|---:|---:|---:|---:|
| 1 | 47.21 | 47.97 | 50.42 (+6.8%) |
| 10 | 22.02 | 22.36 | 23.14 (+5.1%) |
| 64 | 22.03 | 22.29 | 23.81 (+8.0%) |

처리량뿐 아니라 느린 요청 쪽에서도 `P유닛`의 이점은 없다.

## 메모리 결과

PSS 평균은 MiB이며 낮을수록 좋다. 괄호는 `P레이어` 대비 변화다.

| 배치 | `P레이어` | `P어텐션-FFN` | `P유닛` |
|---:|---:|---:|---:|
| 1 | 46.87 | 46.63 (-0.5%) | 47.63 (+1.6%) |
| 2 | 47.13 | 46.82 (-0.7%) | 47.82 (+1.5%) |
| 5 | 37.05 | 39.27 (+6.0%) | 42.37 (+14.4%) |
| 10 | 43.41 | 43.55 (+0.3%) | 48.44 (+11.6%) |
| 16 | 47.67 | 44.08 (-7.5%) | 51.47 (+8.0%) |
| 32 | 48.91 | 49.51 (+1.2%) | 61.05 (+24.8%) |
| 64 | 62.54 | 64.40 (+3.0%) | 89.95 (+43.8%) |

배치 크기 사이의 PSS는 단조롭지 않다. 서로 다른 배치 크기의 절대값을 직선으로
연결해 해석하지 않고, 같은 배치 안에서 P만 비교했다.

`P어텐션-FFN`은 배치에 따라 `P레이어`보다 높기도 낮기도 해서 일관된 메모리
우위가 없다. 반면 `P유닛`은 배치 5 이상에서 항상 더 크고, 배치 32·64에서 격차가
급격히 벌어진다.

### 배치 64에서 무엇이 늘었나

| P | PSS 평균 | PSS 중 익명 메모리 | PSS 중 파일 메모리 |
|---|---:|---:|---:|
| `P레이어` | 62.54 | 34.05 | 28.49 |
| `P어텐션-FFN` | 64.40 | 36.21 | 28.19 |
| `P유닛` | 89.95 | 60.94 | 29.02 |

세 P의 파일 메모리는 28.19~29.02 MiB로 비슷하다. `P유닛`의 추가 27.42 MiB는
거의 전부 익명 메모리에서 생겼다. 즉 더 잘게 나눠 가중치 상주량을 줄이는 효과보다
그래프 경계를 넘는 활성값·계산 버퍼 비용이 컸다. USS와 RSS도 같은 방향이었다.

## 기존 결론과 달라진 점

패딩 제거 전의 [배치 × 파티션 매트릭스](m5-batch-partition-matrix.ko.md)에서도
`unit`이 속도와 메모리 모두 불리했다. 이번 실험은 최종 패킹 뒤에도 **방향이
바뀌지 않았음**을 확인했다.

두 측정은 머신이 다르므로 손해의 크기를 직접 비교할 수는 없다. 이번 결과가 새로
말해 주는 것은 패킹으로 활성값이 작아져도 `P유닛`의 경계 비용이 사라지지 않으며,
큰 배치에서는 다시 커진다는 점이다.

## 검토 결과와 한계

- 시나리오는 매 회 `P레이어 → P어텐션-FFN → P유닛` 순서였다. 따라서 1% 이하의
  차이를 P 자체의 효과로 단정하지 않았다. `P유닛`의 4.5~8.4% 손해는 실행 범위보다
  크고 모든 배치에서 반복돼 이 제한을 넘는다.
- warm·한 머신·한 모델·`mixed_short` 결과다. cold, 다른 CPU, BERT에 일반화하지
  않는다.
- 이 실험은 성능·메모리 실험이다. 파티션별 출력 동등성은 기존 회귀 테스트의
  범위이며, 여기서 새 정확도 수치를 만들지 않았다.
- 호스트에 CMake가 없어 측정 직전 재빌드는 하지 못했다. 사용한 바이너리는 현재
  `gemma3_arch.h`보다 5초 뒤 빌드됐고, SHA-256은
  `ae9264c16e10c4e2b5841fc66d4c4f60eaf39c6d43896db9497a6869d46ad717`이다.
  `P레이어` 수치가 직전 최종 패킹 측정과 일치하는 것도 교차 확인했다.
