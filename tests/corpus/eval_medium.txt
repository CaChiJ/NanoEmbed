Reliable benchmark results depend on controlling more than the code under test. The model file, selected inputs, thread count, compiler options, operating system, and cache state can each move latency or memory independently. A useful report therefore records those conditions alongside the measurements, preserves the exact input identity, and avoids treating samples from one warmed process as independent experiments.
Memory mapping changes when bytes become resident without necessarily changing the mathematical inference graph. During a warm request, pages may already live in the operating system cache and only need minor faults to enter the process page tables. During a genuinely cold request, storage reads and major faults can dominate. Reporting both regimes separately makes the tradeoff visible instead of averaging two different behaviors together.
Token embedding access depends strongly on the corpus. Repeating a small English set tends to revisit a narrow portion of a multilingual vocabulary, while mixed scripts, symbols, emoji, and technical identifiers may touch many distant rows. A streaming benchmark should therefore preserve workload groups and let callers bound each group independently, so a quick development check and a final report exercise the same selection logic.
Percentiles summarize different parts of a latency distribution. The median describes the typical request, while higher percentiles reveal occasional stalls caused by scheduling, allocation, page faults, or storage. They do not become statistically independent merely because thousands of requests were recorded in one process. The run count and selection details remain important context for interpreting every percentile.
Detailed proportional memory accounting is more expensive than reading a process high-water mark. Walking page tables at a short interval can contend with an inference process, especially when the implementation is mapping, faulting, or advising pages. A practical harness keeps detailed sampling optional, labels profiled latency as diagnostic, and still records cheap boundary RSS values during ordinary performance runs.
Correctness checks for an embedding implementation need more than cosine similarity. A vector can preserve direction while carrying the wrong scale, and a small set of dimensions can have large errors hidden by an aggregate score. Maximum absolute error, mean absolute error, root mean square error, norm difference, and cosine similarity together make those failure modes easier to distinguish.
Reproducible reference vectors require precise provenance. Repository names alone are mutable labels, package minimum versions admit different kernels and defaults, and a local model cache may contain several revisions. Recording the resolved revision, file hashes, library versions, device, data type, pooling mode, normalization, truncation length, and generation command turns a fixture into an auditable oracle.
Temporary benchmark inputs should have an explicit lifetime. The runner can materialize only the selected lines, launch the native worker with that file, attach stable selection metadata to the result, and remove the temporary directory whether execution succeeds or fails. Persisting an ephemeral path in the report would be misleading, so the report should use the manifest group as its durable input identity.
Duplicate inputs can silently overweight part of a corpus and distort both latency distributions and page residency. Rejecting duplicates inside a group catches accidental repetition early. The same sentence may intentionally appear in two semantic groups, however, so cross-group duplicates remain independent and each group keeps its own identity in aggregated output.
Selection based on source order makes a small run vulnerable to editorial bias because newly appended lines never appear. Ranking stable text identifiers with a caller-provided seed creates a deterministic subset without depending on file position. The selected identifiers and a digest of the exact materialized bytes then make the workload reproducible even after the temporary file is gone.
Throughput for the current API is single-request throughput rather than batch or concurrent throughput. Dividing completed items by measured wall time is a useful aggregate, but it should be named precisely and interpreted together with the request latency distribution. Future batching work can add separate metrics without retroactively changing what the existing number meant.
Benchmark configuration should fail before expensive model work begins when a requested group is unknown, contains no usable lines, or violates its duplicate policy. Central validation in the orchestration layer gives users one actionable error, prevents partial result files, and ensures every launched worker receives a complete, already verified input selection.
